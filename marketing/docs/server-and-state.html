Server and state

src/server.ts is a single Bun.serve on 127.0.0.1 (port 4173 by default; --host changes the address). It serves public/ as static files (from the copy embedded in a compiled binary, if there is one) and a small JSON API. If the port is taken, the CLI falls back to a free one.

It's one app holding every review you open, each a session in memory at /r/<id>, with its API under /r/<id>/api/. The id is owner/repo/<n> for a PR, owner/repo/<n>@<sha> (or @<from>..<to>) for commits of one, and local/<repo>/<branch> for a branch. src/review.ts builds them: resolve() names the review cheaply (it asks GitHub or git what it is), so its page can open at once, and build() does the slow part in the background; meanwhile its API answers 202 { loading, title }. The running app leaves a lock in ~/.bobby/state/app.lock, and a second bobby hands its review to it (POST /api/open) instead of starting another. A review no page has asked about for 15 minutes is unloaded: its language servers and watchers stop, and it's built again, from the cache, when opened.

Claude's tools (src/mcp.ts): POST /mcp/<token> is an MCP endpoint (streamable HTTP, JSON responses) for one run of Claude, its token made when the run starts and dropped when it ends. Its tools call the review's own API in process: pr_overview, pr_diff, read_file (side: head|base), definition, references, review_threads, history, and in a review report_finding. References in Claude's text are resolved by src/refs.ts into ref://head|base/<path>#L<a>-L<b> links, which the page opens in the code viewer.

App-wide routes: GET / is the home page (public/home.html); GET /api/home gives recents (from ~/.bobby/recents.json, with which are open), settings, who you are and any newer release; GET /api/home/prs?repo=&author=&q= the open PRs waiting on your review, yours and all that involve you, each with whether it's approved (one gh GraphQL search, cached a minute); POST /api/open { arg?, repo?, cwd?, base? } opens a review and answers its id; GET /api/avatar serves GitHub avatars. When gh isn't set up, a failed /api/open answers setup: "gh" and keeps the PR waiting (waiting in /api/home), opened once it is. Setting up gh (src/github.ts) and Claude Code (src/claude.ts): GET /api/gh and /api/claude say where each stands (installed, loggedIn, step, and ask: whether to offer it); POST …/install, …/login (gh: a one-time code to enter on github.com; Claude: a link, then POST /api/claude/code { code }), …/cancel and …/dismiss { never? }.

A session:

interface Session {
  cwd: string | null;        // local clone; null for `bobby open` without --repo
  staticGraph: ReviewGraph;
  claudeGraph?: ReviewGraph; // set when Claude's tree is ready
  state: ReviewState;        // this PR's review progress
  llm: "pending" | "done" | "failed" | "off";
  llmError?: string;
}

The CLI fills claudeGraph and llm from the background Claude job while the server runs.

#Submitting a review

/api/submit posts one GitHub review on the PR's head commit (src/submit.ts):

  • event is COMMENT, APPROVE or REQUEST_CHANGES.
  • Drafts on lines of the diff become comments on those lines (path, line, side, and start_line/start_side for a range).
  • Drafts on lines the diff doesn't show, in a file the PR changes, become comments on the whole file (subjectType: FILE), their body starting with a link to the lines at the head (or base) commit.
  • Drafts in files the PR doesn't change can't be comments on GitHub, so they're appended to the body under "Notes on code this PR doesn't touch".
  • Private notes and review marks are never read here, so they never reach GitHub.
  • With no unsubmitted review of yours on GitHub and no file comments, it's one call: gh api --method POST repos/<o>/<r>/pulls/<n>/reviews --input -. Otherwise GraphQL: the drafts are added to your pending review (addPullRequestReviewThread; one is started with addPullRequestReview if there's none), skipping any already in it, and it's submitted (submitPullRequestReview).
  • Each draft is removed once it's on GitHub, so a retry after a failure halfway posts nothing twice. The answer carries the discussion as read again (discussion, outdated, pending), and on failure the drafts left (comments).

The discussion (reviewComments in src/git.ts) is REST's review comments plus one GraphQL read of the threads: each thread's node id and resolved state, each comment's node id and reactions, comments on whole files (file: true, line 0), and your unsubmitted review (pending) with its comments (pending: true), which REST leaves out.

#On-disk state (src/state.ts)

Everything is JSON under ~/.bobby/ (from os.homedir()):

~/.bobby/
  settings.json                                  UI preferences (free-form; views may add keys)
  state/<owner>_<repo>_<n>.json                  ReviewState for one PR
  cache/<owner>_<repo>_<n>_<sha12>.graphs.json   built graphs for one head commit
  cache/<owner>_<repo>_<n>_<sha12>.tree.<v>.json Claude's raw change tree for one head commit and extraction version
  repos/<owner>/<repo>/                          auto-clones

#ReviewState

interface ReviewState {
  headSha: string;                                // refreshed on load
  marks: Record<string, "reviewed" | "flagged">;  // content key → mark
  comments: Comment[];                            // drafts until submitted
  notes?: PrivateNote[];                          // private notes; never submitted
  lastNodeId?: string;                            // graph node id, for resuming
  lastLevel?: number;                             // zoom level, for resuming
  lastSeenAt?: string;
  note?: string;                                  // parked thought
}

Mark keys are content, not ids, so progress survives force-pushes and tree regeneration:

PageKeys
Changed codethe hash of each of its hunks; the page counts as reviewed when all are
Untouched coderef:<path>:<line>
Low-signal pagethe hashes of all low-signal hunks

Position is stored as a node id (chg:… or ctx:…), which is stable across tree regenerations for the same diff. On boot the UI resumes on the first non-repeat placement of that node.

#Security notes

  • The server binds to 127.0.0.1 unless --host says otherwise, and has no authentication. Anything that can reach it can call it, including /api/submit, which posts as your gh user. guard() refuses a Host that isn't loopback or allowed (hostAllowed, against DNS rebinding) and a write whose Origin isn't the page at that Host.
  • Static file paths are normalised, and anything escaping public/ is a 404.
  • /api/file passes path to git show <sha>:<path>, so it can read any file in the repo at those two commits. That's fine for a local tool, but it's not meant to be exposed.
